# HO-5 改造課題のサンプル解答（課題1〜4）

HO-5 の改造課題は、**ボード側のコードを 1 行も変えません。**
すべて AIブリッジページ（`index.html`）の「AI の設定」タブで行います。

> **それ自体が、この課題でいちばん伝えたいことです。**
> ハードもプロトコルもそのままで、AI に与える指示と出力の形を変えるだけで、
> 装置の役割がまるごと入れ替わります。

貼り付けたら **「適用」** を押してください。次の推論から反映されます。

---

## 課題1　システムプロンプトを書き換えて、まったく別の役割にする

**システムプロンプト**の欄に、以下のどれかを丸ごと貼り替えてください。
出力スキーマは**そのまま**で構いません。`servo` / `status` / `msg` の
意味づけだけが変わります。

### 1-A　ペットの見守り

```
あなたは留守番中のペットを見守る装置です。
室温と湿度から、ペットにとっての快適さを判断してください。

- servo:  飼い主に知らせる緊急度を 0（問題なし）〜180（すぐ帰宅すべき）の整数で
- status: 状態を次のどれかで表す
          GOOD（快適） / DRY（乾燥） / HUMID（蒸れている） / HOT（熱中症の危険） / COLD（冷えすぎ）
- msg:    飼い主のスマホに出す24文字以内の通知文
- reason: その緊急度にした理由を60文字以内で

犬や猫は人間より高温に弱いことを考慮してください。
28℃ を超えたら servo を大きくしてください。
```

### 1-B　植物の水やり判定

```
あなたは観葉植物の世話をする装置です。
温度と湿度から、水やりの必要度を判断してください。

- servo:  水やりの必要度を 0（不要）〜180（今すぐ）の整数で
- status: 状態を次のどれかで表す
          GOOD（good） / DRY（乾燥しすぎ） / HUMID（根腐れの心配） / HOT（葉焼けの心配） / COLD（低温障害の心配）
- msg:    植物の気持ちを代弁した24文字以内のひとこと
- reason: その判断にした理由を60文字以内で

湿度が低く気温が高いほど水の蒸発が速いので、servo を大きくしてください。
湿度が高すぎるときは、水をやらず風通しを勧めてください。
```

### 1-C　勉強部屋の集中度アドバイザー

```
あなたは勉強部屋の環境を整えるアドバイザーです。
温度と湿度から、集中しやすい環境かどうかを判断してください。

- servo:  環境改善の必要度を 0（理想的）〜180（今すぐ換気）の整数で
- status: 状態を次のどれかで表す
          GOOD（集中できる） / DRY（喉が痛くなる） / HUMID（眠くなる） / HOT（暑くて散漫） / COLD（手がかじかむ）
- msg:    勉強中の人に声をかける24文字以内のひとこと
- reason: その判断にした理由を60文字以内で

集中に最適なのは 22〜24℃、湿度 50〜60% です。
二酸化炭素は測れないので、湿度の上昇を人の滞在時間の目安として使ってください。
```

### ここで気づいてほしいこと

- **コードは 1 行も変えていません。** 変えたのは日本語の指示だけです
- それでも `servo` の意味が「換気の必要度」から「帰宅の緊急度」「水やりの必要度」に変わりました
- **`status` の enum はそのままです。** 機械が分岐に使う値の集合は変えず、
  その**解釈**だけを言葉で変えています。だからボード側が壊れません

> **設計の順番が逆だと、これはできません。**
> もし `status` を自由な文字列にしていたら、役割を変えるたびに
> ボード側の分岐も直すことになります。

## 課題2　`temperature` を 0.2 → 1.0 にして、答えのばらつきを見る

「AI の設定」タブの **temperature** のスライダーを動かします。

| 値 | 何が起きるか |
|---|---|
| **0.0 〜 0.2** | 同じ入力なら、ほぼ毎回同じ答え。`msg` の文面まで同じ |
| **0.5** | `msg` の言い回しが変わる。`servo` の値は数度ぶれる程度 |
| **1.0** | 文面が毎回変わる。`servo` も大きくぶれる |
| **1.0 超** | 指示から外れた答えが混じり始める |

**同じ温度・湿度のまま、何度か推論させて比べてください。**
センサーを触らずに「再推論」を押すのが、いちばん分かりやすい確かめ方です。

### どちらが良いという話ではありません

| 用途 | 向く値 |
|---|---|
| 機械を動かす値を決める | **低い**（0〜0.3）。毎回違う角度に動いたら困る |
| 人に見せる文章を作る | **高め**（0.6〜1.0）。毎回同じ文だと飽きられる |

> **本当はこの2つを分けたいところです。**
> 「角度は低い temperature、コメントは高い temperature」と使い分けたくなりますが、
> 1回の推論では 1つの値しか指定できません。
>
> 分けるなら、推論を 2 回に分けることになります。
> ただし推論は 1 回ごとに時間がかかるので、**速さと品質のトレードオフ**です。
> アイデアソンで「AI を呼ぶのは1分に1回まで」のカードを引いたチームは、
> この判断を迫られます。

`topK` も同じ方向の調整です。候補の数を絞るほど答えが安定します。

## 課題3　スキーマに項目を1つ足す（例: `emoji`）

**出力スキーマ**の欄で、2か所に追記します。

```js
const RESPONSE_SCHEMA = {
  type: 'object',
  properties: {
    servo:  { type: 'integer', minimum: 0, maximum: 180 },
    status: { type: 'string', enum: ['GOOD', 'DRY', 'HUMID', 'HOT', 'COLD'] },
    msg:    { type: 'string',  maxLength: 24 },
    reason: { type: 'string',  maxLength: 60 },

    // ★ 1. properties に足す
    emoji:  { type: 'string',  maxLength: 2 }
  },

  // ★ 2. required にも足す（必ず返してほしいなら）
  required: ['servo', 'status', 'msg', 'emoji'],
  additionalProperties: false
};
```

**システムプロンプトにも説明を足してください。**
スキーマだけだと、AI は「何を入れる欄なのか」が分かりません。

```
- emoji:  いまの状態を表す絵文字を1つ
```

### 試してみてほしいこと

1. **`required` に入れずに足す** → 返ってきたり、来なかったりします
2. **`maxLength: 2` を外す** → 絵文字が複数返ってくることがあります
3. **説明をシステムプロンプトに書かない** → 空文字や変な値が入ります

> **スキーマは「形」を縛り、プロンプトは「意味」を伝えます。**
> どちらが欠けても期待どおりになりません。両方要ります。

**余力があれば**、この `emoji` をボード側に送って画面に出してみてください。
ボードの日本語フォント（AlibabaSans_JP24）では絵文字が □ になるので、
`status` から自分で記号を選ぶほうが確実です。
**「AI に何をさせ、何を自分で決めるか」の線引きの練習**になります。

## 課題4　制約なしで実行して、何が返ってくるか観察する

「AI の設定」タブで **出力スキーマの適用を外して**（`responseConstraint` を渡さずに）
実行します。ページ下部にも書いてあります。

### 起きること

```
JSON.parse: unexpected character at line 1 column 1
```

AI は、こんなふうに返してきます。

```
はい、承知しました。現在の室温25.3℃、湿度48.1%の状況ですと…

{ "servo": 40, "status": "GOOD", "msg": "快適です" }

以上となります。何かご不明な点があればお尋ねください。
```

**JSON 自体は合っています。** ただし前後に挨拶と説明がついています。
`JSON.parse` は文字列全体を JSON として読もうとするので、ここで失敗します。

### これが `responseConstraint` を使う理由です

| 方法 | 問題点 |
|---|---|
| 「JSON だけ返して」とお願いする | だいたい守られる。**だいたい**なので、時々破られる |
| 正規表現で `{...}` を抜き出す | 文章中に `{` が出てきたら壊れる。入れ子も扱えない |
| **スキーマで縛る** | **形が保証される。** パースの失敗を考えなくてよい |

> **AI の出力をそのままプログラムに渡せるのは、答えの形をこちらが指定しているからです。**
> 自由に書かせると、そのたびに人間が読んで直すことになります。
>
> これは生成 AI を業務に組み込むときに必ず出てくる論点です。
> **この 2 日間でいちばん実務に近い話が、ここです。**

### さらに観察してみる

制約を外したまま **temperature を 1.0** にすると、形の崩れ方が激しくなります。
「お願いベースの指示が、どれくらい当てにならないか」が体感できます。

## 考えてみよう

**このアプリを「クラウドの AI」で作った場合、何が変わるか。**

| | 端末の中（今回） | クラウド |
|---|---|---|
| ネットが切れたら | 動き続ける | 止まる |
| センサーの値は | 端末から出ない | 送信先に送られる |
| 1秒ごとに呼んだら | 無料。ただし端末が熱くなる | 課金が積み上がる |
| 判断の賢さ | 小さいモデルなりの限界がある | 大きなモデルを選べる |
| 応答の速さ | 往復が無い | 回線とサーバーの状況しだい |
| モデルの更新 | ブラウザーの更新を待つ | すぐ切り替えられる |

**どちらが優れているかではなく、何を優先するかです。**
アイデアソンでは、この表の**左側が有利になる場面**を探すことになります。
