0. はじめに

今日やること

5つのハンズオンを、この順番で進みます。 一本につながっていて、前が終わらないと次が動きません。

内容 時間 何ができるようになるか
HO-0 環境確認 30分（午前） 自分の PC で AI が動くことを確かめる

HO-5 AI を組み込む 60分 AI の判断で機械が動く

HO-5 まで行くと、「話しかけたら機械が動く」ところまで到達します。 そこがゴールです。

コードの置き場所

今日使うコードは、すべてここにあります。

https://github.com/MasaoG/m5ai/tree/main/board

打ち込まずにコピーしてください。 タイピングの練習の日ではありません。 写し間違いを探す時間は、何も生みません。

やり方
コピーする ファイルを開いて、右上の Raw（または「Copy raw file」アイコン）を押す。そこから全選択してコピーします
貼り付ける UIFlow2 のエディターで 全部消してから貼る。古い行が残っていると動きません

⚠️ GitHub の画面上の文字を直接ドラッグして選ばないでください。 行番号まで一緒にコピーされて、Python が必ずエラーになります。 必ず Raw を経由してください。

⚠️ 貼り付けたあと、インデント（行頭の空白）が崩れていないか見てください。 エディターによっては、貼り付け時に自動で字下げを足すことがあります。 Python は字下げで構造が決まるので、ここが崩れると動きません。

ただし 🔧 改造課題は、手で書いてください

本編のコードはコピーで構いません。改造課題だけは、自分で打ってください。 どれも 3〜5 行です。

写すと読み飛ばせますが、打つと読まざるを得ません。 今日いちばん身につくのは、この 3〜5 行のほうです。

サンプル解答は board/answers/ にありますが、まず自分で書いてから開いてください。

進め方

各ハンズオンは 「動かす → 1箇所だけ改造する → 隣の人に説明する」 の3ステップです。3つ目を飛ばさないでください。説明できて初めて理解したことになります。

早く終わった人は、周りで詰まっている人を手伝ってください。教えるのが最も効率のよい復習です。

詰まったときは

5分考えて分からなかったら、手を挙げてください。 遠慮する必要はありません。

各ハンズオンの最後に「つまずいたら」の表があります。症状から原因を引けるようになっているので、まずそこを見てください。巻末の付録B エラー辞典には、エラーメッセージから引ける表もあります。

1つの詰まりに10分以上かけないでください。 メンターが完成コードを渡しますので、先に進んでください。今日のゴールは「全部自力で解決すること」ではなく、「HO-5 まで到達すること」です。

全体を通しての約束

⚠️ 約束1: IDE と AIページは同時に繋げません

シリアルポートは1つのアプリしか掴めません。UIFlow2 / ViperIDE が繋がっている間は、自作のWebページから接続できません（逆も同じ）。

切り替え手順 IDE の「Disconnect」を押す → AIページの「接続」を押す AIページの「切断」を押す → IDE の「Connect」を押す

「接続できません」と言われたら、まずこれを疑ってください。 今日いちばん多い質問です。

⚠️ 約束2: Grove 変換ケーブルは黒と白の2本だけです

赤（5V）と黄は、運営が事前に切断・絶縁してあります。復活させないでください。 赤を繋ぐと外部電源と M5Stack の 5V が衝突し、ボードが再起動します。

⚠️ 約束3: 通電は最後です

配線をすべて終えてから、USB AC アダプターをコンセントに挿してください。

HO-1　Lチカ（LED バー）

所要 25分 ／ ねらい: 開発サイクルを体で覚える

本体の左右の側面には、フルカラー LED が 5 個ずつ、合計 10 個入っています。すりガラス状の導光材と組み合わさっていて、柔らかく光ります。

データ線: G25 ／ 個数: 10 個（SK6812）

G25 は、あとで使う PORT.A（センサー）とも PORT.B（サーボ）ともぶつかりません。

Lチカとは何か 「LED を点滅させること」ではありません。一定の周期で状態を切り替えることです。あとで扱うサーボの PWM も、考え方は同じです。

⚠️ 最初に読むこと — 明るさの上限

set_brightness() は 0〜100 のパーセントです。12% で十分明るく、発熱もほとんどありません。

計算では危ない、でも実測では平気だった

SK6812 は 1 個で最大 60mA 流れます。10 個を白（0xffffff）で 100% 点灯すると 600mA。 Core2 の入力仕様は 5V @ 500mA なので、計算上は超えます。 白は R・G・B すべてが点くため、緑単色の 3 倍です。

ところが実測では、発熱もリセットも起きませんでした。

データシートの 60mA は「最大値」であって、実際の消費はそれより小さいためです。

それでも 12% を使う理由

  1. 100% は明るすぎて直視できません
  2. 計算上の余裕を持たせておくため

「計算では危ないが、実測では平気だった」という差は、ハードウェアを扱うとよく出会います。どちらか一方だけを見て判断せず、両方を知ったうえで余裕のある値を選ぶのが実務の考え方です。

この話は、このあとの HO-3（サーボの電源） でもう一度出てきます。そちらは実測でも問題が起きる側の例です。

これは HO-3 で扱う「サーボの電源を分ける話」と同じ問題です。部品を足すときは、いつも電流を気にする必要があります。 今日の午後だけで 2 回出てくるので、覚えて帰ってください。

手順

1. ハードウェアを追加してブロックで組む

  1. 左のハードウェア一覧から Built-in Hardware Module → RGB を追加
  2. setup に「内蔵ハードウェアの初期化」と「RGB の初期化」を入れる
  3. RGB の初期化ブロックで IO = 25 / number = 10 / type = SK6812 → rgb25 という変数ができます（変数名は IO 番号から自動で決まります）
  4. loop に以下を並べる
rgb25 輝度を設定
rgb25 をすべて設定:色 → 緑
500 ミリ秒停止
rgb25 をすべて設定:色 → 消灯
500 ミリ秒停止

2. 生成された Python を読む

画面右上の切り替えで Python 表示にします。ブロックがどんなコードになったかを必ず見てください。以降、この生成コードが正解の見本です。

3. 生成されたコードを読む

import os, sys, io
import M5
from M5 import *
import m5ui
import lvgl as lv
from hardware import RGB
import time

page0 = None
rgb25 = None

def setup():
    global page0, rgb25
    M5.begin()
    Widgets.setRotation(1)
    m5ui.init()
    page0 = m5ui.M5Page(bg_c=0xffffff)
    rgb25 = RGB(io=25, n=10, type="SK6812")
    rgb25.set_brightness(12)          # 明るさは 1 回でよい

def loop():
    global page0, rgb25
    rgb25.fill_color(0x33ff33)        # 緑
    time.sleep_ms(500)
    rgb25.fill_color(0x000000)        # 消灯
    time.sleep_ms(500)

if __name__ == '__main__':
    try:
        setup()
        while True:
            loop()
    except (Exception, KeyboardInterrupt) as e:
        try:
            m5ui.deinit()
            from utility import print_error_msg
            print_error_msg(e)
        except ImportError:
            print("please update to latest firmware")

✅ 確認 - [ ] 側面の LED が 0.5 秒ごとに緑と消灯で切り替わる - [ ] 本体が熱くならない

押さえておくこと

setup() と loop() に分かれている

役割
setup() 準備。1 回だけでよいこと（初期化、明るさの設定）
loop() 本番。繰り返したいこと

ブロックの並びがそのまま関数になっています。「1 回でよいことは setup() に」が原則です。明るさの設定を loop() に置いても動きますが、毎回同じ値を設定し直すことになります。

色は 16 進数で指定する

0x33ff33 は R=0x33、G=0xff、B=0x33 という意味です。ブロックの「palette 緑」がこの値でした。

0xff0000 赤   0x00ff00 緑   0x0000ff 青
0xffffff 白   0x000000 消灯

全部まとめて / 1 個ずつ

関数 動き
fill_color(色) 10 個すべてを同じ色に
set_color(番号, 色) 指定した 1 個だけ
set_brightness(値) 明るさ

🔧 改造課題

  1. 点滅間隔を 100 ミリ秒にする
  2. 色を白（0xffffff）にして、明るさを少しずつ上げるとどうなるか観察する（熱くなったらすぐ戻す）
  3. 1 個ずつ順番に光らせる（流れる光）
  4. ボタン A を押している間だけ光らせる
  5. ★ HO-2 につながる課題 ★ 10 個をバーグラフとして使う

5番目が本命です。0〜100% を、光る個数 0〜10 個で表します。

def bar(percent, color=0x0078ff):
    n = int(percent * 10 / 100 + 0.5)
    for i in range(10):
        rgb25.set_color(i, color if i < n else 0x000000)

次の HO-2 で湿度を読んだら、これに繋いでみてください。画面を見なくても状態が分かる出力になります。アイデアソンで「画面を見なくてもわかる」の制約カードを引いたチームは、これがそのまま使えます。

HO-2　温湿度センサーを読む

所要 40分 ／ ねらい: I2C でセンサーから値を取る

接続

ENV Ⅲ Unit を PORT.A（本体上部・赤いコネクター） に Grove ケーブルで接続します。

PORT.A は 黄=G32(SDA) / 白=G33(SCL) です。本体上面の PORT.B / PORT.C とは別なので、間違えないでください。

ENV Ⅲ 側も 黄=SDA / 白=SCL なので、ケーブルをそのまま挿せば繋がります。

手順

1. まずスキャンする

コードを書く前に、センサーがバス上に見えているかを確認します。ここを飛ばすと、配線ミスなのかコードのミスなのか分からなくなります。

from machine import I2C, Pin

i2c = I2C(0, scl=Pin(33), sda=Pin(32), freq=100000)   # Core2 PORT.A
print([hex(a) for a in i2c.scan()])

✅ 確認 - [ ] 出力が ['0x44', '0x70'] になっている

0x44 が温湿度センサー（SHT30）、0x70 が気圧センサー（QMP6988）です。ENV Ⅲ の中に2つのチップが入っています。

[]（空）が返る場合は配線を確認してください。PORT.B に挿していませんか。

2. 温湿度を読む

from machine import I2C, Pin
import time

i2c = I2C(0, scl=Pin(33), sda=Pin(32), freq=100000)
ADDR = 0x44

def read_sht30():
    i2c.writeto(ADDR, b'\x2C\x06')     # 単発測定・高精度モード
    time.sleep_ms(20)                   # 測定完了を待つ
    d = i2c.readfrom(ADDR, 6)           # 温度2 + CRC1 + 湿度2 + CRC1
    t_raw = d[0] << 8 | d[1]
    h_raw = d[3] << 8 | d[4]
    t = -45 + 175 * t_raw / 65535
    h = 100 * h_raw / 65535
    return t, h

while True:
    t, h = read_sht30()
    print('{:.1f}C  {:.1f}%'.format(t, h))
    time.sleep(1)

✅ 確認 - [ ] 1秒ごとに温度と湿度が表示される - [ ] センサーに息を吹きかけると湿度が上がる（値が本物である証拠）

2つ目が大事です。数字が出ているだけでは、センサーが動いているとは限りません。

読み解きのポイント

b'\x2C\x06' はセンサーに送る コマンド です。-45 + 175 * raw / 65535 はデータシートに書かれている 変換式 です。

つまりセンサーは「魔法の箱」ではなく、決められた番地に決められたコマンドを送ると、決められた形式で返してくる部品です。ライブラリは、この定型作業を代わりにやってくれているだけです。

🔧 改造課題

  1. 温度が 26℃ 以上なら LED を赤、未満なら青にする（HO-1 の成果を再利用）
  2. ★おすすめ★ 湿度を LED バーグラフで表す（HO-1 の課題5 と合体させます）
from hardware import RGB

rgb25 = RGB(io=25, n=10, type="SK6812")
rgb25.set_brightness(12)

def bar(percent, color=0x0078ff):
    n = int(percent * 10 / 100 + 0.5)
    for i in range(10):
        rgb25.set_color(i, color if i < n else 0x000000)

while True:
    t, h = read_sht30()
    bar(h)                 # 湿度が上がると光る数が増える
    time.sleep(1)

息を吹きかけて、光る数が増えることを確かめてください。画面を見なくても湿度が分かる出力になりました。

  1. 温度と湿度を画面に文字で表示する
  2. time.sleep(1) を time.sleep(0.1) に変えるとどうなるか試す（sleep_ms(20) の意味を考えてみてください）

💬 なぜ測定コマンドを送ったあとに 20ms 待つ必要があるのか、説明してみてください。

📄 サンプル解答: board/answers/ex2_env.py — 課題1〜4。ボタン C でモード切替、課題4 ではボタン A で 1秒 ⇄ 0.1秒 を切り替えます。

つまずいたら

scan() が [] PORT.A に挿さっているか。ケーブルの差し込みが浅くないか

HO-3　サーボを動かす

所要 40分 ／ ねらい: パルス幅で角度を指定する・電源とGNDを理解する

サーボは1人1セットあります。最初から実機で進めます。

冒頭10分（全体）— なぜ電源を分けるのか

運営が組み立てたブレッドボードの実物を見ながら説明を聞いてください。ここは全員で聞く時間です。手は動かさなくて大丈夫です。

要点1: サーボの電源は M5Stack から取れません。 サーボが動き出す瞬間に大きな電流が流れ、M5Stack の電圧が下がって再起動します（ブラウンアウト）。だから電源は USB AC アダプターから別に取ります。

要点2: でも GND だけは繋ぎます。 PWM 信号は「GND を基準にした電圧の変化」で情報を伝えています。基準点が共有されていないと、サーボから見て信号の電圧が何 V なのか分からず、指令と無関係に動きます。

要点3: 330Ω は保険です。 マイコンの出力ピンを守るための直列抵抗です。サーボの信号入力はハイインピーダンスなので、波形には影響しません。

接続する

  1. サーボの3ピンコネクターを、ブレッドボードのピンヘッダーに挿す（橙 赤 茶 の並びを確認）
  2. Grove 変換ケーブルを PORT.B（本体上面の左・黒いコネクター） に挿す
  3. 最後に USB AC アダプターをコンセントに挿す

⚠️ ホーンには紙の指示針だけを付けてください。 車輪やアームは付けません。指を挟まないよう、机の上に置いた状態で動かします。

コードを動かす

from machine import Pin, PWM
import time

servo = PWM(Pin(26), freq=50)    # PORT.B の白 = G26

PULSE_MIN_US = 500
PULSE_MAX_US = 2400
_current = 90

def deg_to_us(deg):
    deg = max(0, min(180, deg))
    return PULSE_MIN_US + (PULSE_MAX_US - PULSE_MIN_US) * deg / 180

def _write(deg):
    servo.duty_ns(int(deg_to_us(deg) * 1000))

def angle(target, step=10, wait_ms=40):
    """突入電流を抑えるため段階的に動かす"""
    global _current
    target = max(0, min(180, target))
    d = step if target > _current else -step
    while abs(target - _current) > step:
        _current += d
        _write(_current)
        time.sleep_ms(wait_ms)
    _current = target
    _write(_current)

angle(90)
time.sleep(1)
angle(0)
time.sleep(1)
angle(180)

⚠️ duty() ではなく duty_ns() を使います。 古い duty()（0〜1023）は分解能が足りず、サーボの動きがカクつきます。

✅ 確認 - [ ] サーボが 90° → 0° → 180° と動く - [ ] 動作中に M5Stack の画面が消えない（消えるなら電源系の配線ミス） - [ ] 動きがカクカクしていない

パルス幅と角度の関係

PWM 周期 20 ms（50 Hz）のなかで、
正パルスの「幅」だけで角度が決まる

  0.5 ms →   0°
 1.45 ms →  90°
  2.4 ms → 180°

周期は常に 20ms のまま変わりません。変わるのは幅だけです。

画面と LED バーにも角度とパルス幅を出しておくと、いま何 µs を送っているかが目で追えます（board/ho3_servo.py を参照）。

自分のサーボを校正する

ここは全員が自分の個体で必ずやってください。 データシート上は 500〜2400µs ですが、個体差でずれます。

  1. _write() を直接呼んで、パルス幅を少しずつ変えてみる
  2. サーボが「これ以上回らない」位置に来たら、そこが端
  3. その値を PULSE_MIN_US / PULSE_MAX_US に書く

⚠️ 「ジー」と鳴り続けたら、すぐ中央に戻してください。

s.duty_ns(1500000)    # 1500µs = 中央

この音は、ギヤが端に当たっているのに動こうとし続けている状態です。放置すると摩耗します。

端を超えても無音で静止する個体もあります。その場合は制御回路が範囲外と判断して無視しているだけで、負荷はかかっていません。同じ値でも個体によって挙動が違います。

✅ 確認 - [ ] 自分のサーボの反応範囲を書き留めた - [ ] 隣の人の値と比べてみた（違っていれば、それが個体差です）

最後の項目をぜひやってください。「データシートに書いてある値がそのまま使えるとは限らない」という感覚は、自分で測って初めて身につきます。

実測しても、教材の値は変えません

検証機での実測例です。

下限 上限
データシート 500µs 2400µs
実測（SG90） 400µs 2600µs

実機のほうが広い範囲に反応しました。それでも PULSE_MIN_US = 500 / PULSE_MAX_US = 2400 のまま使います。

なぜだと思いますか。

理由は3つあります。①個体差があり、全員のサーボが同じ範囲とは限りません。②端では動作が不正確になりがちです。③0〜180度の割り当てが変わるので、同じ「90度」でも指す向きがずれてしまいます。

実測は「知るため」であって、「限界まで使うため」ではありません。

🔧 改造課題

  1. 湿度を角度にマッピングして、実際の湿度計メーターにする
  2. step と wait_ms を変えて、動きの滑らかさがどう変わるか試す
  3. step=180（＝一気に動かす）にすると何が起きるか観察する

💬 なぜ段階的に動かすのか、説明してみてください。

📄 サンプル解答: board/answers/ex3_servo.py — 課題1〜3。課題3（一気に動かす）では Core2 が再起動することがありますが、それが観察対象です。

HO-4　ブラウザーとボードを繋ぐ

所要 45分 ／ ねらい: プロトコルを設計して2つの世界を繋ぐ

このハンズオンが技術的な山場です。

完成形は docs/fig7_ho4_complete.svg です。 先に一度見てから始めると、どこへ向かっているかが分かります。

考え方

PC 側の Chrome とボードは、USB シリアルという1本の細い管で繋がっています。この管を通せるのは文字だけです。そこで「何を、どんな形式で流すか」を先に決めます。

今回は 1行に1つの JSON（JSON Lines） で統一します。

ボード → PC:  {"t":25.3,"h":48.1,"btn":0}
PC → ボード:  {"servo":120,"msg":"換気推奨"}

改行が「1件の終わり」を意味します。これを決めておかないと、途中まで届いたデータと次のデータが混ざります。

手順

1. ボード側のコードを main.py として保存する

ここで初めて「保存」します。 HO-1〜HO-3 は実行するだけで、ボードには何も書き込まれていません。main.py として保存すると、次に電源を入れたときに自動で走るようになります。

消したくなったら、Web Terminal → File → /flash の main.py の Delete です。boot.py は消さないでください。

import sys, select, json, time
from machine import I2C, Pin, PWM
import M5
from M5 import Widgets

M5.begin()

# --- センサー（HO-2） ---
i2c = I2C(0, scl=Pin(33), sda=Pin(32), freq=100000)
def read_sht30():
    i2c.writeto(0x44, b'\x2C\x06')
    time.sleep_ms(20)
    d = i2c.readfrom(0x44, 6)
    t = -45 + 175 * (d[0] << 8 | d[1]) / 65535
    h = 100 * (d[3] << 8 | d[4]) / 65535
    return t, h

# --- サーボ（HO-3） ---
servo = PWM(Pin(26), freq=50)
PULSE_MIN_US, PULSE_MAX_US = 500, 2400
_current = 90
def _write(deg):
    deg = max(0, min(180, deg))
    us = PULSE_MIN_US + (PULSE_MAX_US - PULSE_MIN_US) * deg / 180
    servo.duty_ns(int(us * 1000))
def angle(target, step=10, wait_ms=40):
    global _current
    target = max(0, min(180, target))
    d = step if target > _current else -step
    while abs(target - _current) > step:
        _current += d
        _write(_current)
        time.sleep_ms(wait_ms)
    _current = target
    _write(_current)

def show(msg):
    Widgets.fillScreen(0x000000)
    M5.Lcd.setCursor(10, 100)
    M5.Lcd.print(msg)

# --- メインループ ---
poller = select.poll()
poller.register(sys.stdin, select.POLLIN)
last = 0
angle(90)

while True:
    # PC からのコマンドを受け取る
    if poller.poll(0):
        try:
            cmd = json.loads(sys.stdin.readline())
            if 'servo' in cmd:
                angle(cmd['servo'])
            if 'msg' in cmd:
                show(cmd['msg'])
        except Exception:
            pass

    # 1秒ごとにセンサー値を送る
    if time.ticks_diff(time.ticks_ms(), last) > 1000:
        last = time.ticks_ms()
        t, h = read_sht30()
        print(json.dumps({'t': round(t, 1), 'h': round(h, 1)}))

押さえておくこと

// これは動きません（ページ読み込み時の自動接続）
window.onload = () => navigator.serial.requestPort();

// これは動きます（ユーザーのクリックが起点）

ブラウザーは「ユーザーが意図した操作」でないと、デバイスへのアクセスを許可しません。これは Web API 全体に共通する権限モデルです。カメラもマイクも同じです。

受信は「溜めてから切る」

buf += value;                       // 届いた分を溜める
let i;
while ((i = buf.indexOf('\n')) >= 0) {   // 改行があるだけ取り出す
  const line = buf.slice(0, i).trim();
  buf = buf.slice(i + 1);
  if (line.startsWith('{')) onTelemetry(JSON.parse(line));
}

シリアル通信では、送った 1 行が 1 回で届くとは限りません。途中で切れたり、2 行まとめて届いたりします。だから「改行が来るまで溜める」処理が要ります。

HO-5　AI を組み込む

所要 60分 ／ ねらい: LLM の出力を機械が使える形に固定する

完成形は docs/fig8_ho5_complete.svg です。 HO-4 の図と並べて見てください。変わるのは真ん中の1ブロックだけだと分かります。

やること

センサーの値を 端末内の AI（Gemini Nano） に渡し、判断結果を JSON で受け取ってサーボと画面に反映します。

手順

1. スキーマを決める

先に「AI に何を返させるか」を決めます。

const schema = {
  type: 'object',
  properties: {
    servo:  { type: 'integer', minimum: 0, maximum: 180 },
    msg:    { type: 'string', maxLength: 24 },
    reason: { type: 'string', maxLength: 60 }
  },
  required: ['servo', 'msg'],
  additionalProperties: false
};

minimum: 0, maximum: 180 に注目してください。サーボの物理的な可動範囲を、そのまま AI の出力制約として書いています。 これが今日いちばん覚えて帰ってほしい実装パターンです。

2. セッションを作る

const SYSTEM = `あなたは室内環境アドバイザーです。
温度と湿度から換気の必要度を判断し、
必要度を 0（不要）〜180（至急）の整数 servo で表し、
24文字以内の日本語コメントを msg に入れてください。`;

let base;
async function initAI() {
  if (!('LanguageModel' in self)) throw new Error('Prompt API 非対応');
  const a = await LanguageModel.availability();
  if (a === 'unavailable') throw new Error('この端末では利用できません');

  base = await LanguageModel.create({
    initialPrompts: [{ role: 'system', content: SYSTEM }],
    temperature: 0.2,     // 低いほど毎回同じ答えになる
    topK: 3,
    monitor(m) {
      m.addEventListener('downloadprogress', e =>
        console.log(`${Math.round(e.loaded * 100)}%`));
    }
  });
}

3. 推論する

async function decide(t, h) {
  const s = await base.clone();   // 毎回コピーを作って使い捨てる
  try {
    const out = await s.prompt(`温度 ${t}℃ 湿度 ${h}%`,
                               { responseConstraint: schema });
    return JSON.parse(out);
  } finally {
    s.destroy();
  }
}

✅ 確認 - [ ] センサー値が変わると AI のコメントが更新される - [ ] サーボが AI の返した角度に動く - [ ] 機内モードにしても動く

3つ目を必ず試してください。これがオンデバイス AI です。

押さえておくこと

なぜ responseConstraint を使うのか

一度、制約なしで試してみてください。

const out = await s.prompt(`温度 ${t}℃ 湿度 ${h}%`);   // 制約なし
console.log(out);

AI は「はい、承知しました。換気の必要度は…」のような文章を返してきます。これを JSON.parse() すると例外になり、アプリが止まります。運良く JSON が返っても、servo: 250 のような範囲外の値が混ざればサーボが唸ります。

responseConstraint は「AI の出力を、機械が受け取れる形に強制する」機能です。 ハードウェアを動かすときは必須と考えてください。

なぜ毎回 clone() するのか

Gemini Nano が覚えていられる文脈は、クラウドの大規模モデルよりずっと短いです。センサー値を毎秒投げ続けると、すぐに溢れてエラーになります。

clone() は「システムプロンプトだけ設定済みの、まっさらなセッション」を作ります。使い終わったら destroy() で捨てます。

AI を呼ぶ頻度を落とす

推論は端末の CPU / GPU を使います。毎秒呼ぶと PC が熱くなり、動作が重くなります。

// 悪い例: 毎秒
setInterval(() => decide(t, h), 1000);

// 良い例: 状態が変わったときだけ
if (Math.abs(h - lastH) > 5) {
  decide(t, h);
  lastH = h;
}

「いつ AI を呼ぶか」を設計するのは、実務でそのまま使う判断です。 今日いちばん実務的な学びかもしれません。

多軸を動かす

今回のサーボは1個ずつ、ボードの端子から直接 PWM を出して動かしました。これが2軸、3軸と増えていくと、やり方が変わります。

ボードの端子には数に限りがあり、CPU が全部のパルスを作り続けるのも無駄です。そこで PWM 専用のドライバー基板（PCA9685 など） に仕事を渡し、ボードは「何度にして」と指示するだけにします。I2C 1本で16個まで繋がります。

運営デモの「しるべナノ」が、まさにこの2軸の例です。 気になったら、休憩時間に聞いてください。中身を見せます。

⚠️ Pan-Tilt のリグは運営デモ専用です。 1台しかなく、触り始めると時間を使い切ってしまうので、今回は見るだけにしてください。
